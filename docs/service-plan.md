# 서비스 기획서 — 경량 오류 추적 시스템 (Error Tracking System)

> 작성일: 2026-06-12
> 근거 문서: [error-tracking-checklist.md](error-tracking-checklist.md)
> 버전: v1.0 (초안)

---

## 1. 서비스 개요

### 1-1. 한 줄 정의

소규모 팀이 자체 호스팅으로 운영할 수 있는, **Sentry 동등 수준의 데이터를 수집하는 경량 오류 추적(Error Tracking) 시스템**.

### 1-2. 배경 및 문제 정의

| 문제 | 설명 |
|---|---|
| 외부 SaaS 비용 | Sentry 등 상용 서비스는 프로젝트/이벤트 수에 따라 비용이 증가하며, 소규모 팀에는 과한 요금제 구조 |
| 데이터 주권 | 에러 페이로드에는 사용자 정보·요청 데이터 등 민감정보가 포함될 수 있어 외부 전송이 부담 |
| 과잉 인프라 | 오픈소스 Sentry 셀프호스팅은 Kafka·ClickHouse 등 무거운 의존성을 요구해 소규모 환경에 부적합 |
| 가시성 부재 | 에러 추적 도구 없이는 운영 중인 서비스의 장애를 사용자 제보에 의존하게 됨 |

### 1-3. 해결 방안

- **단일 서버 + PostgreSQL**만으로 동작하는 최소 인프라 구성
- 수집 데이터는 **Sentry 이벤트 스키마와 동등한 수준** 유지 (스택 트레이스, Breadcrumbs, 컨텍스트, 소스맵 복원)
- Docker Compose 한 번으로 배포 가능한 셀프호스팅 패키지

### 1-4. 서비스 규모 전제

- 대상 프로젝트 수: **약 10개**
- 트래픽: 낮음 (프로젝트별 rate limit 분당 300건 수준)
- 확장 전략: 수평 확장 없이 단일 서버에서 운영 (의도적 제약)

## 2. 목표 사용자 및 이용 시나리오

### 2-1. 타깃 사용자

| 페르소나 | 설명 | 핵심 니즈 |
|---|---|---|
| 프론트엔드 개발자 | JS 웹 앱 운영 담당 | 어떤 브라우저/릴리즈에서 에러가 나는지, minify 이전 원본 코드 위치 확인 |
| 백엔드 개발자 | API 서버 운영 담당 | 요청 컨텍스트(URL, 헤더)와 함께 예외 추적 |
| 팀 리드 / 운영 담당 | 서비스 품질 관리 | 신규 이슈·재발 알림 수신, 이슈 우선순위 판단 |

### 2-2. 핵심 이용 시나리오

1. **에러 발생 → 자동 수집**: 사용자 브라우저에서 런타임 에러 발생 → SDK가 자동 캡처해 서버로 전송
2. **이슈 그룹핑 확인**: 같은 원인의 에러 수천 건이 하나의 "이슈"로 묶여 대시보드에 표시
3. **원인 분석**: 이슈 상세에서 소스맵이 복원된 스택 트레이스 + 에러 직전 사용자 행적(Breadcrumbs) + 브라우저/OS 분포를 확인
4. **알림 대응**: 새 이슈 또는 해결된 이슈의 재발 시 Slack/이메일로 즉시 알림 수신
5. **상태 관리**: 수정 배포 후 이슈를 Resolve 처리 → 재발하면 자동으로 Reopen + regression 표시

## 3. 서비스 구조

### 3-1. 시스템 구성

```
[클라이언트 앱 + SDK] ──POST──> [수집 API (Ingestion)]
                                      │  즉시 202 응답
                                      ▼
                              [처리 파이프라인 (Worker)]
                               정규화 → 심볼리케이션 → 그룹핑 → 집계
                                      │
                                      ▼
                                [PostgreSQL]
                                      │
                          ┌───────────┴───────────┐
                          ▼                       ▼
                    [대시보드 (웹 UI)]         [알림 (Email/Slack)]
```

배포 단위: Docker Compose (API + Worker + DB + Front)

### 3-2. 구성 요소별 역할

| 구성 요소 | 역할 |
|---|---|
| SDK (1차 JavaScript, 2차 Python) | 에러 자동 캡처, Breadcrumbs/컨텍스트 수집, 이벤트 전송 |
| 수집 API | DSN 인증, 페이로드 검증, 중복 제거, rate limit, 비동기 처리 위임 |
| 처리 파이프라인 | 정규화, 소스맵 심볼리케이션, 핑거프린팅 기반 이슈 그룹핑, 통계 집계 |
| 대시보드 | 이슈 목록/상세, 검색·필터, 상태 관리, 프로젝트/DSN 관리 |
| 알림 | 신규 이슈·재발·급증 감지 시 이메일/Slack 발송 |

## 4. 핵심 기능 정의

### 4-1. SDK — 이벤트 캡처

**자동 캡처**
- `window.onerror`(런타임 에러), `window.onunhandledrejection`(Promise 거부) 후킹
- 수동 캡처 API: `captureException(err)`, `captureMessage(msg, level)`

**수집 데이터 (Sentry 동등 레벨)**
- **Exception**: 예외 타입/메시지, 프레임별 파일·함수·라인·컬럼, `in_app` 구분(내 코드 vs 라이브러리), 캡처 경로(mechanism), 체이닝 예외(`cause`) 지원
- **Breadcrumbs**: 에러 직전 행적 최근 100개 — DOM 클릭/입력, 페이지 이동, fetch/XHR 요청, console 호출
- **컨텍스트**: user, tags, extra, browser, os, device, request, release, environment, level
- **Scope**: 한 번 설정한 컨텍스트가 이후 모든 이벤트에 자동 첨부

**전송 안정성·프라이버시**
- 클라이언트 생성 `event_id`(UUID)로 중복 제거
- 전송 실패 시 지수 백오프 재시도, 페이지 이탈 시 `sendBeacon` 사용
- `beforeSend` 훅 + 비밀번호/토큰/카드번호 자동 스크러빙 (클라이언트 1차 + 서버 2차 방어)

### 4-2. 수집 API (Ingestion)

- `POST /api/{project_id}/store/` — DSN public_key 인증, CORS 지원
- 페이로드 검증(필수 필드·크기 제한·JSON 파싱), `event_id` 중복 수신 제거
- 프로젝트별 rate limit 초과 시 `429 + Retry-After` (SDK가 준수)
- **즉시 202 응답 후 비동기 처리** — 수집 지연이 클라이언트에 영향 없도록
- 소스맵 업로드: `POST /api/{project_id}/releases/{version}/files/`

### 4-3. 처리 파이프라인 (서비스의 핵심 차별 요소)

1. **정규화** — 누락 필드 기본값, 타임스탬프 보정, 크기 초과 트리밍, 서버 측 민감정보 스크러빙
2. **심볼리케이션** — release + 파일명으로 소스맵 조회 → 압축 코드 위치를 원본 파일/함수/라인으로 복원 + 주변 소스 5줄 첨부 (소스맵 없으면 원본 폴백)
3. **그룹핑(핑거프린팅)** — 스택 트레이스 정규화(in_app 프레임 추출, 가변 경로 제거, 함수명 정규화) 후 해싱 → 동일 지문은 기존 이슈에 카운트 누적, 새 지문은 이슈 생성. 스택 없는 이벤트는 타입+메시지 템플릿으로 폴백, SDK 커스텀 fingerprint 우선
4. **재발 감지** — resolved 이슈에 새 이벤트 유입 시 unresolved 전환 + regression 플래그
5. **집계** — 시간대별 발생 추이, 영향 유저 수(distinct), 태그별 분포(browser/OS/release)

### 4-4. 대시보드 (웹 UI)

**이슈 목록**
- 정렬(최근 발생/빈도/첫 발생), 필터(상태·level·environment·release)
- 텍스트 검색 + 태그 검색(`browser:Chrome` 문법)
- 행별 스파크라인 추이 + 발생 수 + 영향 유저 수, 일괄 해결/무시

**이슈 상세**
- 스택 트레이스 뷰어 (in_app 강조, 프레임 접기/펼치기, 원본 소스 컨텍스트)
- Breadcrumbs 타임라인, 컨텍스트 패널(user/browser/os/device/request)
- 태그 분포 차트, 발생 추이 그래프(24시간/14일)
- 동일 이슈 내 개별 이벤트 페이지네이션, 원본 JSON 보기
- 상태 변경: Resolve / Ignore / Reopen

**관리**
- 로그인/세션 인증, 프로젝트 생성·설정, DSN 표시

### 4-5. 알림

- 트리거 3종: ① 새 이슈 ② 재발(regression) ③ 급증 감지
- 채널: 이메일, Slack incoming webhook
- 프로젝트별 알림 규칙 설정 UI
- 디바운싱: 동일 이슈 알림 시간당 1회 제한
- 메시지에 이슈 제목·링크·발생 수·환경 포함

## 5. 데이터 정책

| 항목 | 정책 |
|---|---|
| DSN 형식 | `https://{public_key}@{host}/{project_id}` |
| 이벤트 페이로드 | Sentry Event Payload 포맷 차용 |
| 이벤트 최대 크기 | 200KB ~ 1MB (확정 필요) |
| 원본 이벤트 보관 | 90일 후 자동 삭제 (cron 스케줄러 — **미구현 시 DB 무한 증가, 필수**) |
| 이슈 요약 보관 | 영구 |
| 소스맵 아티팩트 | 오래된 릴리즈 정기 정리 |
| 민감정보 | 클라이언트(beforeSend + 자동 스크러빙) + 서버 2차 스크러빙, IP 기록 여부 정책 별도 결정 |

### 데이터 모델 (핵심 테이블)

- `projects` — 이름, 플랫폼, public_key(DSN)
- `issues` — fingerprint(프로젝트별 UNIQUE), 제목, 상태, level, first/last_seen, times_seen, 영향 유저 수
- `events` — event_id(UUID), issue_id, 원본 페이로드(JSONB), release, environment
- `releases` / `sourcemaps(artifacts)` — 릴리즈별 소스맵 관리
- `users_affected` — 이슈별 영향 유저 distinct 집계
- `comments` / `activity` — 이슈 메모·상태 변경 이력 (선택)

## 6. 개발 로드맵

체크리스트의 "권장 개발 순서"를 단계(Phase)로 재구성:

| Phase | 범위 | 완료 기준 (Definition of Done) |
|---|---|---|
| **Phase 1 — 최소 루프 (MVP)** | DB 스키마 + 수집 API + 기본 핑거프린팅 + 이슈 목록 UI | curl로 보낸 에러가 이슈로 묶여 목록에 보인다 |
| **Phase 2 — JS SDK 기본** | onerror/unhandledrejection 캡처 + 스택 트레이스 수집 | 실제 브라우저 에러가 자동으로 수집된다 |
| **Phase 3 — 이슈 상세** | 스택 뷰어, 이벤트 페이지네이션, 상태 변경 | 이슈 하나를 끝까지 분석·처리할 수 있다 |
| **Phase 4 — 데이터 심화** | Breadcrumbs + 컨텍스트(Sentry급 데이터의 핵심) | 에러 직전 행적과 환경 정보가 함께 보인다 |
| **Phase 5 — 알림** | 신규/재발/급증 알림, Slack·이메일 | 새 이슈 발생 시 5분 내 알림 수신 |
| **Phase 6 — 소스맵** | 업로드 CLI/플러그인 + 심볼리케이션 (난이도 최고, 의도적으로 후순위) | minify된 에러가 원본 코드 위치로 표시된다 |
| **Phase 7 — 운영 안정화** | 보관 기간 삭제 cron, 백업, 헬스체크, Docker Compose 정리 | 무인 운영이 가능하다 |

## 7. 의도적 비범위 (Out of Scope)

소규모 전제에 따라 다음은 **만들지 않는다**:

- Kafka 등 메시지 큐 분리 → DB 트랜잭션 + 백그라운드 작업으로 대체
- ClickHouse 등 전용 이벤트 저장소 → PostgreSQL JSONB로 충분
- 다중 워커 수평 확장
- Performance/Tracing, Session Replay, Profiling (오류 추적과 별개 제품 영역)

## 8. 성공 지표 (KPI)

| 지표 | 목표 |
|---|---|
| 에러 수집 → 대시보드 노출 지연 | 평균 10초 이내 |
| 그룹핑 정확도 | 동일 원인 에러의 오분류(이슈 분산) 체감 최소화 — 운영 중 수동 병합 요구 빈도로 측정 |
| 알림 지연 | 신규 이슈 발생 → 알림 수신 5분 이내 |
| 운영 비용 | 단일 서버 1대로 프로젝트 10개 커버 |
| SDK 오버헤드 | 페이지 로드 영향 최소화 (번들 크기·초기화 시간 측정) |

## 9. 리스크 및 대응

| 리스크 | 영향 | 대응 |
|---|---|---|
| 보관 기간 삭제 미구현 | DB 무한 증가로 서비스 정지 | Phase 7 이전이라도 cron 삭제를 조기 구현 (체크리스트상 "필수" 표기) |
| 그룹핑 품질 저하 | 이슈가 잘게 쪼개지거나 과도 병합 | 정규화 규칙(가변 경로 제거, 메시지 템플릿화) 우선 투자, 커스텀 fingerprint 탈출구 제공 |
| 소스맵 심볼리케이션 난이도 | 일정 지연 | 마지막 Phase로 격리, 폴백(원본 표시) 먼저 보장 |
| 자기 에러 무한 루프 | 추적 시스템 자체 에러가 자기 자신에게 보고되며 폭주 | 자체 에러 로깅 경로 분리 |
| 민감정보 유출 | 법적·신뢰 리스크 | 클라이언트+서버 이중 스크러빙, beforeSend 훅 제공 |

## 10. 미결정 사항 (Open Questions)

체크리스트 0장 "사전 설계 결정" 중 확정이 필요한 항목:

1. 지원 플랫폼 범위 — 1차 JavaScript 확정, 2차 Python 시점
2. 이벤트 1건 최대 크기 — 200KB vs 1MB
3. 이벤트 보관 기간 — 90일 기준 확정 여부
4. IP 주소 기록 여부
5. `console.error` 자동 후킹 포함 여부 (선택 항목)
